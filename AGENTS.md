# Agent memory (Helvety)

## Learned User Preferences

- After substantive auth or flow changes, run a verification pass and remove stale or unused code before treating the work as done.
- When login or security behavior changes, keep READMEs, code comments, and user-facing legal copy aligned with the implementation.
- Run full pre-deploy checks via root `ci:release` (format-check, lint, type-check, test, then `build` with `SKIP_ENV_VALIDATION=1` so local builds succeed without `.env`; placeholders are disabled when `VERCEL=1`). Use `ci:check` when a build is not needed (it omits `build`).
- Prefer fixing consistency and correctness within the current architecture over large rewrites unless product requirements call for a different shape.
- Do not add AI co-author or similar attribution trailers to git commits.

## Learned Workspace Facts

- Next.js 16 apps here use `proxy.ts` (not `middleware.ts`) for lightweight request handling (`createSecurityProxy`: CSP, CSRF bootstrap, and Supabase auth cookie refresh when `sb-*` session cookies are present). Treat authentication as defense-in-depth in server actions, route handlers, and pages.
- **Read-only server actions** (no `csrfToken` passed to `authenticateAndRateLimit`) skip CSRF by design; they still require an authenticated Supabase session and use read-style rate limits (`readRateLimitConfig`, default `RATE_LIMITS.READ`). Bulk export uses `RATE_LIMITS.EXPORT` via `readRateLimitConfig`. Defense-in-depth relies on **session cookies** (SameSite defaults with the SSR client) and **Next.js Server Actions** host/origin behavior for cross-site safety. Prefer passing `csrfToken` for state-changing actions; optional future tightening: require CSRF on high-value reads (e.g. export) by threading the token from `CSRFProvider`.
- E2EE apps (**contacts**, **notes**, **tasks**): each default `page.tsx` should `await requireE2eeAppPageAuth("/…")` from `@helvety/shared/e2ee-page-auth` (wraps `requireAuth` with the canonical path). Layouts gate `EncryptionGateApp` on `initialUser` but **do not** replace this page-level guard — add `requireE2eeAppPageAuth` to any new protected route.
- **Passkey / encryption server actions (two surfaces):** `@helvety/shared/encryption-actions` (`getPasskeyParams`, `getEncryptionParams`) backs `EncryptionGateApp` via `@helvety/ui/encryption-gate-app` on E2EE zones. `apps/auth/app/actions/encryption-actions.ts` owns login/bootstrap (`hasEncryptionSetup`, `getPasskeyParams` with credential-read rate limits, CSRF-gated `saveKeyCheckValue`). Both read `user_passkey_params` through `@helvety/shared/user-passkey-params-db` (`fetchUserPasskeyParamsForUser`) so PostgREST handling stays aligned when the query changes.
- **Vercel Speed Insights:** only `apps/web` uses `VercelAnalyticsWithSpeedInsights`; other Next apps use `VercelAnalytics` from `@helvety/ui/vercel-analytics` (marketing-only RUM choice).
- **Startup `instrumentation.ts`:** contacts/notes/tasks/auth/store validate `lib/env` in `register()`; `apps/web` and `apps/pdf` omit it until they introduce server-side secrets—mirror the contacts pattern when adding `lib/env`.
- For failures from `catch` or API error objects, prefer `logger.logUnexpectedError(scope, error, context?)` from `@helvety/shared/logger` over `logger.error("message", error)` so production error tracking uses `captureException` (string-first `logger.error` routes to `captureMessage`). Keep `logger.error(message, { ... })` when logging structured metadata without a primary `Error`.
- Vitest mocks of `@helvety/shared/logger` must expose `logUnexpectedError` (and `warn` / `error` when the module under test calls them); assert `logUnexpectedError` with `toHaveBeenCalledWith(scope, …)` where logging is part of the contract. Route handlers that only use `logger.warn` do not need a `logUnexpectedError` stub.
- Use `isUuidString` from `@helvety/shared/uuid-string` for fast ID parameter checks in server actions; keep Zod `.uuid()` on payloads where schemas already validate full objects. `entity-links` shares the same UUID rules via that helper.
- **Supabase PostgREST typings:** `@supabase/postgrest-js` deprecates `.returns<T>()` on query builders. Use `.overrideTypes<T, { merge: false }>()` at the end of **multi-row** `select` chains when app-level row types should replace inference. For **`.single()`** / **`.maybeSingle()`** reads, rely on generated `Database` row types from `supabase-js` (avoid `.single().overrideTypes<OneRow>()` and `.overrideTypes<Row[]>().single()`—current typings reject the first pattern and the second drops `.single()` on the builder). Vitest Supabase mocks should mirror the real chain (`overrideTypes` vs terminal `single()`).
- `packages/config/eslint.mjs` exports `createEslintConfig` / `createPackageEslintConfig` for apps and packages, and a **default** flat config so `eslint --config eslint.mjs .` lints the config package itself (with `tsconfig.json` including `vitest.server-only-mock.ts`). **eslint-plugin-react-hooks** 7.x (pulled in via `eslint-config-next`) enables `react-hooks/set-state-in-effect` and `react-hooks/refs`; those are turned **off** in `createEslintConfig` until call sites are refactored for React Compiler–style constraints.
- Auth login UI maps steps via `apps/auth/lib/login-flow-stepper.ts`; server-driven next-step after OTP and in callback flows uses `apps/auth/lib/auth-step.ts` (`resolveAuthStep`) from passkey and encryption readiness.
- Login OTP length and validation are centralized in `apps/auth/lib/otp-code.ts` (6–8 digits) and kept aligned with `otp-actions`.
- Passkey presence for login bootstrap must use the same trusted read path as OTP and callback flows (`user_auth_credentials` via scoped admin where RLS blocks ordinary client reads).
- Session-aware login on `/auth/login` (`resolveAuthenticatedEmailBootstrap` in `apps/auth/lib/login-email-bootstrap.ts`) enforces the required sub-step globally (`encryption-setup` or `passkey-signin`) for all destinations, so non-E2EE app entry points still complete passkey before redirect. **`EncryptionGate`** still redirects to auth with `force_login=1` via `redirectToLoginOnce` when explicit re-auth is needed.
- This monorepo uses Bun and Turbo for scripts; `apps/auth` unit tests cover stepper helpers, auth-step resolution, and related actions.
- Batch reorder and encrypted export row caps for **tasks**, **notes**, and **contacts** server actions use `ACTION_LIMITS` from `@helvety/shared/constants`—keep those limits defined in one place.
- **`@helvety/ui`** has Vitest coverage for selected primitives (e.g. `Button`, `ListSearchField`, `tiptap-utils`); run `bun run test --filter=@helvety/ui` from the repo root.
- **`@helvety/shared/client-search`** provides normalized substring + multi-token AND matching for **in-browser** list filtering on decrypted rows only (tasks, notes, contacts main lists). Search queries stay in React state, not the URL.
- Store **account deletion** post-delete verification queries live in `apps/store/lib/account-deletion-verification.ts` (consumed by `account-actions`); unit tests mock the admin client.
- **`hasAccountDeletionVerificationFailures`** is covered for `residualRows`, `residualErrors`, and `authStillExists`; contact **`reorderContacts`** tests assert Zod rejects payloads over `ACTION_LIMITS.MAX_REORDER_ITEMS` so server-action caps stay aligned with `@helvety/shared/constants`.
- **`jsdoc/require-jsdoc`** is turned off for specific **link** actions/hooks/panels and **PDF pipeline** files via glob overrides in `packages/config/eslint.mjs`—prefer that over file-wide `eslint-disable` when adding similar modules.
- Vitest `test:coverage` scripts require `@vitest/coverage-v8` (declared in the root `package.json` devDependencies so it hoists to all workspaces); keep Vitest and `@vitest/coverage-v8` on the same minor line (e.g. 4.1.x) to satisfy peer ranges.
- Root `deps:check` runs Knip for unused files and dependency analysis; `knip.json` uses the Knip 6 schema.
- `bun run deps:security:floors` enforces minimum versions for Next.js, React, `react-dom`, `@supabase/supabase-js`, and `@simplewebauthn/server` via [`scripts/check-security-dependency-floors.mjs`](scripts/check-security-dependency-floors.mjs); update that script when raising those dependencies so CI and docs stay aligned.
- **`apps/*/lib/env.ts` (auth, store, contacts, notes, tasks):** Server `SUPABASE_SECRET_KEY` plus Upstash URL/token are read with `readServerUpstashEnvFromProcess()` from `@helvety/shared/env-validation`, together with `isCiBuildPlaceholderEnvEnabled()` / `hasRealServerUpstashEnv()` / `getCiPlaceholderServerUpstashEnv()` so root `ci:release` can build without a full local `.env` while still validating any vars that are set.
- Contacts main list (`ContactList`) shows all fixed category sections even when the address book is empty, matching Tasks list behavior for built-in stages (`EntityList`). Notes uses the same grouped-list pattern with fixed categories (Personal, Work, Other) via `EntityList` and `DEFAULT_NOTE_CATEGORIES`. While the main-list search field has text, reorder/drag is disabled and `emptySearchMessage` is shown when nothing matches (see app READMEs). Vitest covers those UX dimensions for **Contacts** (`contact-list.test.tsx`), **Notes**, and **Tasks** (`entity-list.test.tsx` in each app)—not only the search-empty path.
- **Store catalog** (`apps/store/lib/data/products.ts`) is the source of truth for product copy and listing count; public downloads use `lib/packages/config.ts`. When adding a product, align **Impressum**, **Privacy**, **Terms** (if product class changes), root/store **READMEs**, and **layout/manifest** descriptions so marketing and legal text stay accurate.
- `getClientIP()` in `apps/auth/app/actions/auth-action-helpers.ts` returns `string | null`; callers (passkey and OTP actions) **must fail closed** when it returns `null` — never fall back to a shared rate-limit bucket. Store download actions use `getTrustedClientIp` directly with the same fail-closed pattern.
- Logger (`@helvety/shared/logger`) and auth-logger (`@helvety/shared/auth-logger`) redact PII keys (`email`, `phone`, `address`) alongside secrets. Prefer structured metadata (`logger.info("message", { key })`) over template-literal string embedding for new log call sites.
- All 7 `public` schema tables have RLS enabled with full CRUD policies; all use `FORCE ROW LEVEL SECURITY` (including `entity_links`). `user_auth_credentials` has a single "Deny all access" policy for the `public` role and is read via scoped admin only.
- SECURITY DEFINER row-limit triggers (`check_contacts_row_limit`, `check_items_row_limit`, `check_notes_row_limit`) all use `SET search_path TO ''` and grant EXECUTE only to `postgres`, `anon`, `authenticated`, `service_role` (no PUBLIC grant). `handle_new_user` is restricted to `postgres` and `service_role`.
- `get_auth_user_by_email` is restricted to `postgres` + `service_role`; `handle_auth_user_data_cleanup` and `purge_auth_user_owned_data` are restricted to `postgres` only.
- Storage bucket `packages` is private with a "Deny all direct access" policy; downloads are generated via signed URLs in server actions with IP-based rate limiting.
- `user_profiles.email` is the only plaintext PII column in `public` — intentional because it mirrors `auth.users.email` for login bootstrapping. All other user data uses `encrypted_*` columns (E2EE).
- `supabase/getSupabase.sql` exports the full DB schema for local audits; output goes to `supabase/supabase.json` (gitignored). Re-export after any schema or policy change.
